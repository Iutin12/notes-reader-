## Что это за проект

«Нотера» — локальный тренажёр чтения и проигрывания нот.

- Пользователь загружает PDF, MusicXML/MXL или MIDI.
- PDF распознаётся локально через Audiveris OMR.
- MusicXML отображается через OpenSheetMusicDisplay (OSMD), воспроизводится через Web Audio с фортепианными сэмплами.
- Есть подсветка текущей позиции, режимы проигрывания, экранная клавиатура, обучение, сохранение произведений в `localStorage` и экспорт MusicXML.
- Есть Docker-вариант и Electron-установщики для macOS/Windows без Docker.

## Стек и ключевые файлы

- Frontend: React / Vinext / TypeScript.
- Страница приложения: `app/page.tsx`.

## Важная Windows-проблема и исправление

Симптом: Windows Electron-приложение показывало HTML без CSS/JavaScript. В версии `0.1.1` проверка старта показала, что `GET /` работает, а `/assets/*.css` не работает.

Причина: Vinext `0.0.50` создаёт ключи кэша статики через `path.relative`. На Windows это даёт `assets\\file.css`, а браузер запрашивает `/assets/file.css`.

Исправление уже добавлено:

1. `scripts/patch-vinext-static-cache.mjs` меняет путь на
   `path.relative(...).split(path.sep).join("/")`.
2. В `package.json` добавлен `postinstall`, автоматически применяющий патч после `pnpm install` — в том числе на GitHub Windows runner.
3. `package.json > build > extraResources` явно кладёт `dist` в `server/dist`.
4. `desktop/main.cjs` проверяет, что после старта доступны HTML и первый CSS/JS asset. При ошибке выводится диалог, а не «голая» страница.
5. Версия приложения поднята до `0.1.2`; в заголовке окна видно версию.

Важно: после `pnpm install` проверять наличие строки ниже:

```bash
rg 'split\(path\.sep\).*join' node_modules/vinext/dist/server/static-file-cache.js
```

Для проверки Windows-пакета без Windows можно собрать распакованный пакет:

```bash
pnpm exec electron-builder --win dir --x64 --publish never
rg -a 'split\(path\.sep\).*join' release/win-unpacked/resources/app.asar
```

## Реализованные функции

- Обязательная загрузка PDF/MusicXML/MXL/MIDI.
- Локальный Audiveris OMR в Docker и desktop-дистрибутивах.
- Генерация превью всех PDF-страниц, прогресс обработки, сообщения об ошибках страниц.
- Извлечение названия файла и попытка чтения BPM из MusicXML/распознанного PDF.
- Выбор BPM вручную; поле можно очистить и ввести число.
- Сохранение произведений в `localStorage`.
- Отображение MusicXML и воспроизведение фортепианными сэмплами.
- Длительности нот, аккорды, подсветка текущих нот и курсор.
- Клик по партитуре для перехода к месту проигрывания.
- Режимы: всё произведение, по одной ноте, по тактам, фрагмент, обучение.
- Метрононом, повтор, громкость, скорость/темп.
- Экранная клавиатура: левая рука фиолетовая, правая зелёная, одна нота в обеих руках — разделённый цвет.
- Горячие клавиши: Space play/pause, стрелки переход, R repeat, M metronome, A auto-scroll, K keyboard guide, T training.
- Автопрокрутка отключаемая; на её поведении было много правок — не ломать без ручной проверки.
- macOS DMG и Windows NSIS установщики без Docker.

## Редактор партитуры: текущее состояние

Пользователь хочет редактор как копию одной строки партитуры, чтобы:

- перетаскивать любую ноту по высоте и времени;
- добавлять и удалять ноты;
- задавать длительность;
- видеть исходное положение;
- сохранять изменения в MusicXML, отображение и звук.

Сейчас есть первая рабочая реализация в `app/page.tsx`:

- Кнопка `✎ Редактор` открывает модальное окно для текущего такта и активной партии.
- Отрисовываются верхний и нижний нотоносцы, ключи, тактовые деления.
- Ноты добавляются кликом по пустой области; перетаскиваются по времени и диатоническим ступеням.
- Есть выбор длительности 1/16, 1/8, 1/4, 1/2, целая; удаление выбранной ноты.
- Изменённая нота получает серый пунктирный силуэт исходной позиции.
- Для нот за пределами нотоносца есть добавочные линейки и подпись `до4` и т.п.
- Близкие ноты в аккордах сдвигаются вправо, чтобы не сливаться.
- Сохранение выполняется через `applyMeasureEditorToMusicXml()` и затем `parseMusicXml()` — партитура и проигрывание должны обновляться.

Последние связанные коммиты:

- `11e5428` — отображение MusicXML после сохранения правок.
- `ee96408` — staff-based measure editor.

- `0a2059f` — вертикальное позиционирование по строкам стана.
- `bc19d14` — добавочные линейки и раздвижение аккордов.
- `b77a4a6` — точные границы/размер выбранного такта.

### Важное: редактор ещё требует ручной проверки

Пользователь сообщил, что в исходной партитуре и редакторе ноты всё ещё могут стоять по-разному. Последний коммит `b77a4a6` исправляет наиболее вероятную причину: ранее использовался общий `score.beatsPerMeasure` и остаток `startBeat % score.beatsPerMeasure`; это ломается при затакте и сменах размера.

В `lib/music.ts` к `MusicEvent` добавлены опциональные поля:

- `measureStartBeat?: number`
- `measureBeats?: number`

Парсер MusicXML их заполняет. Редактор использует их, но это изменение ещё не проверено пользователем на его реальном файле.

Ограничения текущего редактора:

- Редактируется один такт одной выбранной партии.
- Упрощённо пересобираются ноты выбранного такта; сложные многоголосные места, связки, артикуляции, лиги, акцидентные знаки, паузы и ритмические группы могут быть потеряны/упрощены.
- Высота в UI определяется по диатонической позиции; диезы/бемоли пока не имеют отдельного редактора.
- Визуализация редактора — самописная CSS-разметка, не полная нотная гравировка OSMD. Долгосрочно лучше строить интерактивный слой поверх SVG, отрендеренного OSMD, и связывать графические ноты с MusicXML.

Рекомендуемый следующий шаг:

1. Попросить пользователя после сборки `b77a4a6` проверить конкретный такт.
2. Получить скрин исходного такта и редактора одного и того же такта.
3. Если позиции расходятся, добавить тест MusicXML с затактом/изменением размера в `tests/music.test.ts`.
4. Затем перейти к OSMD/SVG-предпросмотру строки, чтобы копия визуально была идентична источнику.

## История проблем, о которых сообщал пользователь

- Неполное/ошибочное распознавание PDF — фундаментальное ограничение Audiveris OMR. Приложение должно сообщать о нераспознанных страницах, не молча пропускать их.
- Audiveris может падать на отдельных страницах. Уже добавлены сообщения и повторные попытки; гарантировать корректное OMR для любого PDF нельзя.
- Были проблемы с задержками/микропаузами и Safari audio; используются WebAudio/сэмплы и планирование событий, но сложные OMR-партиуры могут содержать неверные ритмы.
- Автопрокрутка ранее прыгала; пользователь отдельно просил не ломать её. В desktop она должна следовать за позицией только при включённой настройке/клавише A.
- macOS DMG не подписан Apple Developer certificate. Gatekeeper может показать «приложение повреждено». Ранее пользователю предлагали `xattr -cr`, но пользователь хочет, чтобы команды не требовались. Полное решение требует платной Apple Developer подписи + notarization.

## Правила работы и коммуникации

- Пользователь русскоязычный, предпочитает, чтобы изменения сразу делались, коммитились в `main` и запускали pipeline.
- До каждого действия с инструментами кратко писать обновление в commentary.
- Для локальных правок использовать `apply_patch`, не `cat`/редиректы.
- Перед коммитом запускать как минимум `pnpm lint`, `pnpm typecheck`, `pnpm test`; перед рискованными UI/packaging изменениями — `pnpm build`.
- После успешного commit/push в ответе выводить Codex git-директивы.
- Не использовать destructive git-команды (`reset --hard`, `checkout --`) без прямого запроса.
- Репозиторий может быть грязным; чужие изменения не трогать.
